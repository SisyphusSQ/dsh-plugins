# npm 认证、凭据与中断恢复

涉及认证或部分发布时使用本参考。npm UI、2FA 和 token 产品规则会变化；操作前以 npm 官方文档和当前页面为准，不根据旧截图猜测。

## 认证选择

### Trusted Publishing

重复发版优先使用 Trusted Publishing/OIDC：

- 将信任限制到精确的 source repository、workflow 文件和 environment；
- 为 CI 保留最小 `contents: read` 与 `id-token: write` 权限；
- 不在仓库 secrets 中长期保存 npm publish token；
- 首次切换后仍执行版本、dist-tag、integrity 和消费端回读。

### 交互式 2FA

已有 npm 登录会话且能够完成 OTP/WebAuthn 时，优先使用交互式认证。不要索取或转述用户的一次性密码；让官方 npm CLI 或官方页面完成挑战。

### 临时 granular token

仅在 Trusted Publishing 和交互式 2FA 都不可用时使用。创建 token 是独立的高影响外部写操作，必须有明确授权。

- 有效期选择当前 UI 能提供的最短期限；
- 只授予发布所需权限，只选本次目标包；
- 首次发布、包尚不存在且 UI 无法逐包选择时，才考虑临时扩大包范围，并在发布后立即撤销；
- 不授予组织管理、用户管理或与发布无关的权限；
- 不为“以后可能再用”保留 token。

## 凭据处理

生成 token 后：

1. 只使用官方复制控件或安全的凭据交接通道获取值。
2. 不读取、打印或记录页面完整 DOM、`innerText`、网络日志或剪贴板历史来提取 token。
3. 不把 token 放进聊天、工具参数、命令行参数、shell history、Git、Issue、PR、Release notes 或普通日志。
4. 如需本地 npm 配置，使用本轮专用的绝对路径文件，权限设为 `0600`，并通过 npm 支持的配置文件机制引用。
5. 日志只记录 token 的用途、创建时间、到期时间、权限范围和清理状态，绝不记录 token 值或可逆片段。

一旦 token 值出现在聊天、DOM 快照、终端输出、日志或提交中，按已泄露处理：立即停止发布、撤销 token、创建替代凭据，并检查暴露范围。不要继续使用“看起来还安全”的已暴露 token。

不要假设发布 token 能撤销自己。发布前保留一个不依赖该 token 的管理会话或官方账号登录，以便完成服务端撤销。

## 认证失败

遇到 `E401`、`E403`、OTP/2FA 错误或 scope 不足时：

1. 停止后续包，不要无界重试。
2. 通过无凭据命令或 registry HTTP 回读已经发布的包和版本。
3. 检查当前 registry、账号、组织权限、token 包范围、2FA 模式与 token 到期时间。
4. 修复认证后，重新核对剩余发布矩阵；不要再次发布已经存在的同版本。

## 部分发布恢复

对每个目标包建立状态表：

| 状态 | 处理 |
|---|---|
| registry 不存在目标版本 | 修复认证/配置后可继续发布 |
| 目标版本存在且 integrity、shasum 一致 | 记为已发布，跳过该包 |
| 目标版本存在但摘要不一致 | 立即停止，按供应链事件调查；不可覆盖同版本 |
| dist-tag 未指向目标版本 | 单独评估并获得授权后修正 tag |
| 发布命令失败但 registry 已存在一致版本 | 以 registry 为准，记为成功并继续闭环回读 |

不要自动 `npm unpublish`。撤包会影响已有消费者，并且受 npm 时间与依赖规则限制；除非用户明确授权且已完成影响评估，否则保留已发布版本，修复剩余步骤。

## 清理与回读

发版完成或中止后都要：

1. 撤销本轮临时 token，并从 npm 账号页面或官方接口回读其已撤销/不存在。
2. 删除本轮创建的专用 npm 配置文件，并确认路径不存在。
3. 清理临时目录；保留用户缓存与既有配置。
4. 检查 Git diff、构建产物和日志，确认没有凭据或本机路径残留。
5. 如果无法完成服务端撤销，把任务标为“发布完成但凭据清理未完成”，记录 token 元数据和明确的待办，不宣称全流程结束。
